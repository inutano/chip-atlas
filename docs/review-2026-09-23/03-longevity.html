総括 (まず読むべき点)

結論。アプリ本体 (Sinatra + Sequel + SQLite + 素の TypeScript、外部 CDN ゼロ、依存 gem 12 個) は 10 年運用に向いた構造になっている。一方で 「新版を本番に置き、再起動やインスタンス入れ替えを生き延び、データを更新する」ための運用経路がリポジトリに存在しない。ここが最大のリスクで、初回デプロイの時点で顕在化する。順に:

  1. デプロイ経路が旧版のまま (初回デプロイで失敗)。script/deploy/deploy.sh は origin/master を checkout し、存在しない rake pj:load_metadata (新版は metadata:load) を呼び、Gemfile に無い unicorn を起動し、npm run build を行わない。script/systemctl/ の起動スクリプトも rbenv + unicorn 前提。docs/setup.md も旧版 (LONG-OPS-01, LONG-RB-04, LONG-OPS-15)。
  2. Puma を起動・再起動・監視する仕組みが無い。systemd unit も docker-compose の restart: も無く、OS 再起動やクラッシュ (今回のレビュー中にもローカルで sqlite3 の SIGBUS で落ちて手動再起動した) で止まったままになる (LONG-OPS-02)。
  3. nginx 設定と host 認可が本番トポロジと矛盾する。本番は ALB で TLS 終端 (ACM 証明書) しインスタンスの nginx は :80 だが、config/nginx/chip-atlas.conf は 80→443 リダイレクトと Let's Encrypt の証明書パスを持つ (配置すると nginx -t 失敗かリダイレクトループ)。さらに production の host_authorization は Host が IP のとき /health にも 403 を返すため、deploy.sh の IP 直叩きヘルス待ちは通らず、ALB ヘルスチェックも同じ条件 (LONG-OPS-03/04, LONG-RB-01)。
  4. コンパイル済み JS が git 管理外で、どのデプロイ経路にもビルド工程が無い。Dockerfile は COPY するだけ (.dockerignore が frontend/ を除外)、CI はビルドするが成果物を残さない。5 年後に 1 行のテンプレート修正を出すにも Node + esbuild 環境が必要で、ビルド忘れは /health 200 のままページだけ死ぬ (LONG-FE-01, LONG-OPS-13)。
  5. 時限爆弾。本番 OS (nginx 1.18 ⇒ Ubuntu 20.04/22.04) の EOL で deploy.sh の apt-get upgrade が失敗、Docker ベース (Debian 13) と Ruby 4.0 (EOL 2029 年頃) も同様。Gemfile に版制約が無く、sqlite3 ネイティブ gem は Ruby < 4.1 限定、BUNDLED WITH 2.5.3 は Ruby 4.0 の Bundler と食い違う (LONG-OPS-05, LONG-RB-10)。
  6. ディスク・メモリの単調増加。Ruby Logger 'daily' は古いログを消さない、Puma のログは追記のみ、logrotate 無し、access_log には EA に投入された BED 本文 (最大 16 MB) まで丸ごと記録される。metadata/<timestamp>/ は更新のたびに ~660 MB 蓄積、sra_cache の掃除は呼ばれない、プロセス内キャッシュ (検索総件数、TSV 行列) は無期限 (LONG-OPS-06/07, LONG-RB-03/06, LONG-RB-19/24)。
  7. データ更新の手順が無く、そのまま実行するとサイトが数分間「空」になる。rake metadata:load はテーブル DELETE をトランザクション外で行い、失敗すると空のまま (/health は 200)。更新後も起動時固定のキャッシュ (ゲノム一覧、総件数) は再起動まで古い。更新はどこにもスケジュールされていない = データはデプロイ時点で凍結 (LONG-OPS-08, LONG-RB-02/09)。
  8. 「動いているように見えて壊れている」経路。NCBI の一時障害が 30 日キャッシュされる、DataProxy が上流の全障害を「not found」に変換する、/status の feature フラグをフロントエンドが参照しない、ジョブ結果ページが 503 を捨てて永久ポーリングする、ファセット読み込み失敗が画面に出ない (LONG-RB-05/08, LONG-FE-02/06)。
  9. ドキュメントの陳腐化。agents/demo/llms.txt/openapi の TAIR10、外部リンクの 404 (node status)、旧版向けの文書・スクリプトの残存 (LONG-FE-04/05, LONG-RB-23)。

優先して手を入れるべき最小セット。(1) Puma 用の systemd unit (Restart=always) と、新版用のデプロイ手順 (git checkout → bundle install → npm ci && npm run build → rake metadata:load を別ファイルに構築して差し替え → systemctl restart) を書き、deploy.sh・systemctl・docs/setup.md の旧版記述を全て置き換える。(2) ビルド済み JS をコミットするか Dockerfile を multi-stage にして Node ビルドを含める。(3) nginx 設定を ALB 終端に合わせ、/health を host 認可の例外にする (または nginx で Host を固定)。(4) logrotate (access_log / puma.*.log) と metadata/ の世代管理、access_log からのボディ記録除外。(5) SraService の失敗結果を短い TTL にする、DataProxy の障害を 502/503 に分ける、結果ページの 503 処理。(6) Ruby/gem/OS の EOL をカレンダーに入れる (Ruby 4.0: 2029 年、Ubuntu 22.04: 2027 年 4 月)。

高 本番の host_authorization が ALB ヘルスチェック / IP 直叩きの /health を 403 にする LONG-RB-01

顕在化時期: 初回デプロイ時 (ALB ターゲット登録時) / インスタンス入れ替え時場所: app.rb:70-72 (set :host_authorization, { permitted_hosts: ['.chip-atlas.org'] }), config/nginx/chip-atlas.conf:56-58 (/health を Host $host のまま転送), script/deploy/deploy.sh:283-284 (curl http://$IP/health)確認状況: ローカルで再現 (MockRequest, RACK_ENV=production)。ALB 側の Host 値は 推定 (AWS 仕様に基づく)。
内容
Sinatra 4.1+ の host_authorization は Rack::Protection::HostAuthorization を挿入し、許可外 Host に 403 "Host not permitted" を返す。本番モードで Rack::MockRequest により再現: Host: chip-atlas.org → 200、Host: www.chip-atlas.org → 200、Host: 10.0.0.5 / 10.0.0.5:80 / localhost:9292 → 403、X-Forwarded-Host: chip-atlas.org を付けても 403。ALB のヘルスチェックはターゲット IP を Host に載せる (AWS の仕様) ので、nginx を経由しても Puma で 403 になり、ターゲットは unhealthy のまま登録されない。deploy.sh:283 の IP 直叩きも同じ理由 (加えて nginx :80 は return 301 なので 301) で 5 分待って die。旧アプリには host 制限が無かったため、この経路は一度も実運用で通っていないと推定。運用者から見ると「デプロイが health check で止まる」「ALB が全ターゲット unhealthy」。
推奨対策
host_authorization に allow_if: ->(env) { env['PATH_INFO'] == '/health' } を追加する (Rack::Protection::HostAuthorization は :allow_if を受け付ける: rack-protection/host_authorization.rb:30,56)。または nginx の /health location で proxy_set_header Host chip-atlas.org; に固定する。deploy.sh の待機は -H 'Host: chip-atlas.org' と -k https:// に変える。

内容
DELETE は各々オートコミットされ、WAL モードの読み手は即座に空テーブルを見る。その後 load_json_index (実測 2.2 s, RSS 845 MB) と 867,660 行のタブ読込・INSERT が 1 トランザクションで走る間、ユーザには「Home の実験数 0」「検索 0 件」「/view が全部 404」「Peak Browser のメニュー空」が見える。ロードが例外で止まると (例: 不正 UTF-8 が 1 バイトでもあると split("\t") が ArgumentError: invalid byte sequence を投げる — コンテナで確認。現行スナップショットは 0 行) DELETE 済みのまま終わり、/health は database: ok で 200 を返し続けるので LB は異常を検知しない。また稼働中に rake を同一ファイルへ走らせると、ロード中の SraCache.set (/view のキャッシュミス時) が SQLite の busy_timeout 5 s (Sequel 既定, sequel/adapters/sqlite.rb:150) 超過で Sequel::DatabaseError → /view が 500。プロセス内キャッシュ (RB-09) も更新されない。メモリの database.sqlite.latest/.rebuild/.verify という別ファイル運用はローカルの慣行で、手順としてはどこにも書かれていない。
